## propose — 2026-09-08  [✅]
Outcome: Drafted the full artifact set describing why a "National" agreement must not reach
pay-and-stamp (stamp duty is state law, so there is no duty to compute and no state in which
to buy the certificate, against a ToS that guarantees no second bill), and how to stop it —
a config allowlist of checkout-eligible states enforced server-side, with `IN` still fully
usable for drafting and preview. `openspec validate --strict` passes for this change.

Decisions:
- **Two gate points, not one.** Grounding found `finaliseAndPay()`
  (CaptureForm.vue:806) calls `POST /{id}/finalise` and then `POST /{id}/payment/order` in
  one user action, and finalise is what places the order and creates the signing request in
  `PDF_GENERATED` — i.e. what enters the staff stamp queue. Gating only checkout would still
  queue an `IN` agreement for a certificate nobody can buy. This answers the open question
  carried into the flow: **yes, finalise needs the gate too.**
- **Mirror `CONTACT_REQUIRED` rather than invent a shape.** It is already documented as
  "one rule... applied at both gates" (order creation + signing initiation), implemented as
  `PaymentOrderService.requireReachableParties` (line 92, called at line 138 ahead of order
  reuse as well as creation). The new check follows that structure exactly.
- **Distinct `ConflictException.Kind.JURISDICTION_UNSUPPORTED`**, not folded into
  `PAYMENT_REQUIRED`, on `PaymentGate`'s own stated principle that a different person fixes
  each 409.
- **Allowlist, not an `IN` denylist.** A denylist would pass every test written today and be
  silently wrong the moment Karnataka appears — it would default to eligible with nothing
  computing its duty.
- **Fail closed on a null `templateId`** (legacy rows / fixed-fields-only API clients). Found
  during grounding, not in the original brief. `AgreementDocumentService.dimensionsFor`
  treats null as "use the documents default", which is right for rendering and exactly wrong
  for fulfilment.
- **Empty/absent allowlist refuses everything** — a misconfigured deploy stops checkout
  rather than opening it. Mitigated by a committed default and a startup log line.
- **Frontend reads eligibility from the server** (new read-only list), never a hardcoded
  client list. Rejected: an `eligible` flag on the `documents` catalog API (pushes a
  `signing` policy into `documents`, inverts the module dependency); a hardcoded frontend
  list (a second source of truth that drifts — the same defect class `npm run terms:doc`
  exists to prevent).
- **ToS work is an addition, not a retraction.** Audited: LandingPage.vue:51 makes no
  national-coverage claim (it argues *against* one national PDF) and termsOfService.ts has no
  supported-states clause at all. So the CR adds one.
- **Overlap named:** this is the narrow shippable slice of `state-stamp-duty-quoting`
  (4/4 artifacts, not applied), whose spec already says "unsupported states fail closed...
  their templates do not reach checkout". That change later supersedes this allowlist with
  real per-state duty rules.

Halts: none — the one product decision was resolved with the user before the flow began.
Follow-up CRs: none new. Existing successor is `state-stamp-duty-quoting`.

## review round 1 — 2026-09-08  [⛔ → resolved, artifacts revised]
Outcome: Multi-persona review (architect / senior engineer / security) grounded in the real
code found two blocking issues and several majors. All are now folded into the artifacts;
two required a user decision and both were put to the user and answered.

Decisions (user-answered halts):
- **Null `templateId` refusal is a BREAKING change — ACCEPT IT, fail closed.**
  `CreateAgreementRequest` documents `state`/`type` as optional and ships a pre-dimensions
  constructor, so a dimension-less agreement is a supported contract today with a working
  path to paid fulfilment; the gate removes it. The create surface stays permissive
  (mandatory dimensions would be a second, larger API break — explicitly out of scope) and
  ~9 integration fixtures that create bare agreements and finalise are migrated (task 10.1),
  with one kept asserting the 409 so the break is pinned by a test (10.2).
- **Extend the gate to the two staff-facing steps.** A staff `waive` sets `WAIVED`, which
  satisfies `PaymentGate` — the ONLY control on `POST /api/staff/estamp`
  (`StampIntakeService:186`) and `POST /api/signing/*/request` (`SigningRequestService:121`).
  So staff could still buy a real SHCIL certificate in no defined state, which is exactly the
  hazard the proposal names (undefined fulfilment, not merely unpaid fulfilment). Both call
  sites already invoke `PaymentGate.require`, so the addition is one line each. The CR now
  has FOUR gate points, not two.

Decisions (folded without a halt):
- **Cross-CR contradiction with `state-stamp-duty-quoting` — fixed in the requirement text.**
  That change lets a customer on a NATIONAL template pick the property's state, which becomes
  the duty jurisdiction, and refuses only when unchosen. A flat "IN is ineligible" would
  archive into the living spec as a contradictory unconditional rule. The requirement is now
  written against the **duty jurisdiction** rather than the template's state dimension, with
  "IN is not itself a duty jurisdiction" — which is what the successor spec says (D2).
- **A SETTLED order is reported, not refused** (D4). The spec previously said refuse on every
  call including reuse. `reusableOrder`'s settled branch (`PaymentOrderService:174-176`)
  exists to report an already-paid order; refusing there would 409 a customer who had already
  paid — the ToS hazard inverted, shipped by the CR that exists to prevent it. This is where
  the `CONTACT_REQUIRED` analogy stops (contacts freeze at settlement; config does not).
- **Use `TemplateCatalogApi#find`, not `detail`** (D6). `detail` throws for an unknown OR
  non-published id, so a since-unpublished TG template would refuse with a misleading 404
  rather than the promised 409.
- **`Agreement.templateId()` is package-private** (`Agreement.java:494`) and
  `AgreementResponse` carries none — a rule outside `signing.agreement` cannot read it today.
  Added as an explicit task (1.4), not left as an implementation surprise.
- **Fail-closed is an implementation obligation, not free.** The properties type must
  null-normalize in its compact constructor (`PaymentProperties:31` precedent) or an absent
  config block NPEs into a 500 instead of refusing; and codes must be case/whitespace
  normalized or a lower-case `tg` in config causes a fail-closed outage (D5, tasks 1.1-1.2).
- **The new eligibility endpoint needs a home and a matcher** (D9, tasks 6.1-6.2): a static,
  anonymous route in `signing.api` with its own `SecurityConfig` entry — `anyRequest()
  .denyAll()` means an unmatched path silently 403s and the disclosure degrades to nothing.
- **Failed eligibility fetch degrades the MARKING, not the gate** (D9). Marking everything
  draft-only would deter payable customers over a transient network error; enforcement is
  server-side regardless.
- **Refusals are logged, not audited to a table** (D8). No money, no PII, a pre-commitment
  event — a table would be over-engineering; the log also answers "which jurisdiction is
  customers asking for next".
- **Webhooks / reconciliation / recovery stay ungated, stated explicitly** so it does not
  read as an oversight — they record work already committed.
- **Pre-archive check widened from `PAID` to "at or beyond finalise"** — a `PDF_GENERATED` IN
  row already sits in `awaitingStampQueue`, so `PAID` alone undercounts the real exposure.

Halts: two, both resolved by the user in-turn (above).
Follow-up CRs: none new. Successor remains `state-stamp-duty-quoting`.

## apply — gate troubleshooting  [⚠️ self-inflicted, resolved]
A `./gradlew check` run failed with 26 of 952, in `RecoveryIntegrationTest` and
`PaymentGateIntegrationTest` — neither related to this change. Under a long
`UnsatisfiedDependencyException` chain the real cause was `ContainerLaunchException` →
`RetryCountExceededException` → `TimeoutException`: **Testcontainers could not start containers.**

Cause was operational and mine: I ran several Gradle builds concurrently and stopped one
mid-flight, stranding **25 orphaned Testcontainers containers** — the exact accumulation failure
CLAUDE.md documents (invisible, random names, they pile up until the Docker engine wedges).
Cleared with `scripts/sweep-test-containers.sh --force` (25 → 0) plus a volume prune reclaiming
659 MB, then re-run sequentially.

Two lessons for this repo's workflow, worth keeping:
- **Never run concurrent Gradle builds here.** Beyond the daemon lock, each aborted run strands
  container pairs, and the resulting failures surface far from the cause — in unrelated test
  classes, as a dependency-injection error rather than a Docker one.
- **A deep `UnsatisfiedDependencyException` in this suite is usually not a wiring bug.** Read to
  the BOTTOM of the cause chain; the Spring frames are noise wrapped around a container timeout.

Corroborating evidence that the code is not at fault: the two runs that isolated the new code
both passed cleanly — `JurisdictionGateIntegrationTest` 10/10 and `StampIntakeApiIntegrationTest`
27/27, the latter including both new stamp-gate cases.
