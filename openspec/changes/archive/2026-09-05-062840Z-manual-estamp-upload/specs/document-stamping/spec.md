## MODIFIED Requirements

### Requirement: Procure a stamp through the StampProvider seam

The system SHALL attach an e-stamp through a vendor-neutral `StampProvider` seam, parallel to
the `EsignProvider` seam. The seam SHALL take a **staff-supplied scanned certificate and its
certificate metadata** and return a stamp result carrying the **certificate number**, the
**composited stamped PDF** bytes, the **duty amount**, the **jurisdiction**, and a
**dutyPaid** flag. All implementation specifics SHALL live behind the interface in an adapter
package inside the `signing` module. No code outside the `signing` module SHALL reference the
adapter package and `ModularityTests` SHALL remain green.

The stamp SHALL be procured **out-of-band by staff** on the SHCIL portal; the system SHALL NOT
generate a stamp, call a stamp-procurement API, or hold any SHCIL credential. Because the
certificate represents duty actually paid, the result SHALL set `dutyPaid = true`.

#### Scenario: Attachment returns a stamp result

- **WHEN** the system attaches a staff-uploaded certificate to an agreement's draft PDF
- **THEN** the seam returns a stamp result with the certificate number, the composited
  stamped PDF bytes, the duty amount, the jurisdiction, and `dutyPaid = true`

#### Scenario: No stamp is ever generated by the system

- **WHEN** a signing request needs a stamp and none has been uploaded
- **THEN** the system does not generate, synthesise, or procure one, and no external stamp
  endpoint or credential is used

#### Scenario: Module boundaries hold

- **WHEN** the module-boundary verification runs
- **THEN** no module outside `signing` references the stamp provider adapter package and
  the verification passes

### Requirement: Composite the e-stamp onto the agreement PDF

The system SHALL composite the stamp onto the agreement's draft PDF using a JVM PDF library
(Apache PDFBox), producing a new stamped PDF. The composition SHALL **prepend the uploaded
scanned certificate image as page 1**, scaled to fit the page while **preserving its aspect
ratio** and without upscaling beyond its native resolution, then **overlay a per-page header**
carrying the **certificate number** on the draft pages. The resulting stamped PDF SHALL have a
page count of `1 + (draft page count)`.

Composition SHALL NOT mutate the stored draft or the stored scan; both SHALL remain available
unchanged. The overlay SHALL be positioned relative to **each draft page's own media box** and
respect that page's rotation, so it lands in-frame for any page size or orientation
(A4/Letter/landscape/rotated); the overlay text SHALL use a Standard-14 font (the certificate
number is ASCII), requiring no bundled font file. Chromium/Playwright SHALL NOT be required
for this step - page-prepend and text overlay are not complex-script *shaping*, so a pure-JVM
PDF library is appropriate.

#### Scenario: Stamped PDF prepends the scanned certificate

- **WHEN** a draft PDF of N pages is composited with an uploaded certificate scan
- **THEN** the stamped PDF has `N + 1` pages, with the scanned certificate as page 1

#### Scenario: Scan is fitted without distortion

- **WHEN** a scan whose aspect ratio differs from the page is composited
- **THEN** it is scaled to fit within the page bounds with its aspect ratio preserved and is
  not stretched, cropped, or upscaled beyond its native resolution

#### Scenario: Certificate-number overlay appears on the document pages

- **WHEN** a draft PDF is composited with certificate number `IN-KA12345678901234X`
- **THEN** the stamped PDF's document pages carry a header overlay bearing that certificate
  number

#### Scenario: Original draft and scan are not mutated

- **WHEN** a draft PDF is composited into a stamped PDF
- **THEN** the stored draft bytes and the stored scan bytes are unchanged and still
  retrievable

#### Scenario: Overlay lands in-frame for non-A4 / landscape pages

- **WHEN** a draft whose pages are landscape or a non-A4 size is composited
- **THEN** the overlay is positioned relative to each page's media box and remains within the
  page bounds (no off-page or clipped overlay)

### Requirement: Untrusted-draft parsing fails closed

Compositing SHALL parse **both untrusted inputs** defensively: the user-uploaded draft PDF
(only its `%PDF-` magic bytes were validated at upload) and the staff-uploaded certificate
scan (validated per `estamp-intake`). Every parse, decode, or composition failure - an
**encrypted/password-protected** PDF, a **corrupt or truncated** PDF or image, a **zero-page**
PDF, or a structurally pathological (deeply nested / huge object-count) PDF - SHALL be caught
and surfaced as a stamping failure, so the signing request transitions to `STAMP_FAILED` (per
`signing-request`).

It SHALL NOT produce an unmapped server error, hang the request thread, or exhaust JVM memory.
Byte size is bounded by the upload ceilings on both inputs, and the parser SHALL run with a
bounded memory/scratch setting so a large-but-legal file cannot exhaust the heap.

#### Scenario: Encrypted draft fails closed

- **WHEN** compositing is attempted on an encrypted/password-protected draft PDF
- **THEN** stamping fails cleanly (no unmapped 500) and the signing request goes
  `STAMP_FAILED`

#### Scenario: Corrupt or zero-page draft fails closed

- **WHEN** compositing is attempted on a corrupt/truncated or zero-page draft PDF
- **THEN** stamping fails cleanly and the signing request goes `STAMP_FAILED`

#### Scenario: Undecodable scan fails closed

- **WHEN** compositing is attempted with a certificate scan that cannot be decoded
- **THEN** stamping fails cleanly, the signing request goes `STAMP_FAILED`, and no partial
  stamped PDF is stored

### Requirement: Stamping uses sandbox/dummy data only and logs no PII

Stamping SHALL operate only on the agreement PDF, the uploaded certificate scan, and the
certificate metadata. It SHALL NOT read, write, or log Aadhaar numbers, OTPs, virtual IDs, or
signer PII.

The scanned certificate carries **party names and a property description**, so logging around
stamping SHALL NOT emit the scan bytes, the stamped PDF bytes, or any certificate metadata
value verbatim; the certificate number SHALL appear only **redacted** (last 4 characters).
Only redacted identifiers (e.g. the agreement id) MAY be logged in full.

In this repository stamping SHALL be exercised with **synthetic fixture images and fabricated
certificate numbers only**; no real SHCIL certificate, credential, or portal call SHALL be
introduced. Real duty payment happens out-of-band in production operations, which is why a
production stamp result carries `dutyPaid = true` while repository fixtures do not represent
real duty.

#### Scenario: No PII or document bytes in stamping logs

- **WHEN** the system logs around stamp attachment and composition
- **THEN** no Aadhaar/OTP/VID/signer PII, no scan or PDF bytes, and no verbatim certificate
  metadata appear in the logs; the certificate number appears only in redacted form

#### Scenario: Repository exercises stamping with dummy data only

- **WHEN** stamping is exercised in this repository's tests
- **THEN** only synthetic fixture images and fabricated certificate numbers are used, and no
  SHCIL endpoint or credential is contacted

## ADDED Requirements

### Requirement: Uploaded certificate scan stored under an agreement-scoped key

The uploaded certificate scan SHALL be stored as a blob via the existing object-storage
(`BlobStore`) seam under a key **derived from the internal agreement id**, alongside the
existing `stamped/{agreement-id}.pdf`. The key SHALL NOT be derived from the certificate
number or any other external identifier (key-hygiene). Scan bytes SHALL NOT be stored in
PostgreSQL - only the storage key is persisted.

The scan SHALL be retained after composition as the evidence artifact for the attached stamp.

#### Scenario: Scan is written to object storage under an agreement-scoped key

- **WHEN** a staff user uploads a certificate scan for an agreement
- **THEN** the scan bytes are written to object storage under a key derived from the internal
  agreement id
- **AND** only the key (not the bytes) is persisted in the database

#### Scenario: Scan is retained after composition

- **WHEN** the stamped PDF has been composited and stored
- **THEN** the original scan remains retrievable from object storage

## REMOVED Requirements

### Requirement: Deterministic synthetic stamp serial

**Reason**: The synthetic BW-series serial existed only because the v1 stamp was generated by
the system. The stamp is now a real SHCIL certificate purchased by staff, and its **certificate
number** is the authoritative identifier - supplied at upload, not derived. A derived serial
would be actively misleading on a document evidencing real duty.

**Migration**: The `serial` field on stamp info is repurposed to carry the SHCIL certificate
number. No agreement carries a real stamp yet (the synthetic adapter set `dutyPaid = false`),
so no production data migration is required; any existing BW-series values are dummy data.
Uniqueness is now enforced by a database constraint on the certificate number rather than by
derivation from the agreement id.
