Validate that a change's implementation accurately reflects its spec artifacts.

**Input**: Optionally specify a change name. If omitted, check if it can be inferred from conversation context. If vague or ambiguous you MUST prompt for available changes.

**Steps**

1. **Select the change**

   If a name is provided, use it. Otherwise:
   - Infer from conversation context if the user mentioned a change
   - Auto-select if only one active change exists
   - If ambiguous, run `openspec list --json` to get available changes and use the **AskUserQuestion tool** to let the user select

   Always announce: "Validating change: <name>"

   **If you cannot prompt** (this skill is normally run inside a subagent, which has no
   `AskUserQuestion`) and the name is ambiguous, do **not** guess a change and do not hang:
   stop and return "change name not resolvable — caller must pass it explicitly". The caller
   (`openspec-flow`) is required to pass the resolved name for exactly this reason.

2. **Read spec artifacts**

   Run `openspec status --change "<name>" --json` to get artifact paths and schema.

   Read all available spec artifacts for the change:
   - `openspec/changes/<name>/proposal.md` — requirements, goals, scope
   - `openspec/changes/<name>/design.md` — design decisions, approach, constraints
   - `openspec/changes/<name>/tasks.md` — planned implementation steps
   - `openspec/changes/<name>/specs/` — any capability specs (if present)

   Skip artifacts that don't exist — not all schemas produce all artifacts.

3. **Build the evidence set from the change's own manifest — not from git history**

   The question "which code belongs to THIS change?" is answered **declaratively by the
   change's own artifacts**, never inferred from commits. `tasks.md` names the files it
   creates (`V16__zoop_esign_payment.sql`, `ZoopEsignProvider`,
   `LeegalityEsignProviderWireMockTest`); the coverage matrix names the tests. Read those.

   This is the whole reason the skill no longer parses diffs. A commit range cannot
   isolate a change that shares commits with its siblings, sees nothing that is still
   uncommitted, and answers differently depending on which branch you happen to be on.
   A manifest has none of those properties: it reads the same on a feature branch, on the
   default branch, with ten changes in flight at once, and with nothing committed at all.
   **Never reintroduce a `git diff <base>` here** — `main...HEAD` and friends are how a
   sibling CR's code came to satisfy this CR's checkpoints and get reported as "verified".

   **3a. Derive the file set.**
   - Every path named in `tasks.md` — source files, migrations, tests, config. Take them
     literally; resolve a bare class name to its file with
     `grep -rl "<Identifier>" backend/src frontend/src`.
   - Every test named in the coverage matrix (`## Coverage` in `tasks.md`, written at
     review time — see the `review-spec` skill).
   - The capability directories under `openspec/changes/<name>/specs/` translated to their
     module trees: `backend/src/main/java/in/agreementmitra/<module>/` (the modules are
     `signing`, `documents`, `identity`, `rules`), `frontend/src/` for UI concerns.
   - Endpoints named in the proposal's `## Impact` → `grep -rl "<path fragment>" backend/src`.

   Read those files **at the current working tree**. Do not reconstruct historical state.

   **3b. Cross-check for unplanned work — the one thing the manifest cannot tell you.**

   ```bash
   git status --porcelain -uall
   ```

   `-uall` is not optional: plain `--porcelain` collapses an untracked *directory* to one
   line (`?? backend/src/main/java/in/agreementmitra/payments/`), so a whole new package —
   exactly what an apply stage creates — would appear as a single entry.

   Compare the changed/untracked paths against the manifest from 3a:
   - A path in the manifest and in the working tree → expected.
   - A manifest path with no corresponding file → a gap (see step 5's task check).
   - A changed path this change's tasks do not mention → **check the other active changes
     before calling it unplanned:**

     ```bash
     grep -rlF "<path or class name>" openspec/changes/*/tasks.md
     ```

     More than one change is routinely in flight in the same working tree (this project runs
     several CRs per branch, and a teammate may be working the default branch). A path another
     active change's `tasks.md` claims is **that change's work — not this one's stray edit**.
     Attribute it to that change and move on; do not report it.

     Only a path that **no** active change's tasks mention is unplanned work — and that is the
     signal worth having: scope creep, accidental edits, and debug leftovers live there. It is
     an observation, not automatically a gap, but it must appear in the report, naming the paths.

   Never run `git add` (or `git add -N`) to make untracked files visible — banned by the
   git guardrails, and unnecessary: you are reading files, not diffing them.

   **Budget guard.** If the file set is large, read first the files under the modules and
   capabilities the artifacts name, then the rest as budget allows — and **say in the report
   that you truncated, and which files you skipped.** Silent truncation is a false "verified".

   **3c. Record what you resolved** — report this in the header (step 7): the number of
   manifest paths resolved, how many were read, and the count of changed-but-unplanned paths.

4. **Run the structural check**

   ```bash
   openspec validate --strict --type change --no-interactive "<name>"
   ```

   `--type change` disambiguates a change whose name also matches a spec; `--no-interactive`
   matters because this skill usually runs inside a subagent that **cannot answer a prompt** —
   without it an ambiguous name can hang the run.

   **A non-zero exit means findings, not a crash** — capture the output and carry it into the
   report; do not abort the run.

   This checks artifact structure (requirements have scenarios, deltas are well-formed),
   independent of and complementary to the code cross-check. Record the result in the report:
   a structural failure is worth surfacing even when the code cross-check is clean.

5. **Extract checkpoints from spec artifacts**

   From the artifacts, extract a list of concrete checkpoints to verify. These are:

   **From proposal.md:**
   - Each stated goal or requirement
   - Explicit scope inclusions ("this change will...")
   - Explicit scope exclusions ("out of scope: ...") — verify these were NOT implemented

   **From design.md:**
   - Each named design decision (e.g., "use X pattern", "store Y in Z", "validate using W")
   - Architectural constraints ("must not...", "always...", "never...")
   - Integration points mentioned (APIs, models, services touched)

   **From specs/ (if present):**
   - Each `### Requirement:` — the normative statement that becomes the spec of record.
   - Scenarios are **not** checkpoints here. Every `#### Scenario:` already has an explicit
     disposition in the `## Coverage` matrix (`COVERED` / `GROUPED` / `MANUAL` / `WAIVED`),
     agreed at review time before any code was written. Your job is the next paragraph, not
     to re-litigate the matrix.

   **From tasks.md — the conformance check.**

   A ticked box is a *claim* by the same agent that wrote the code: the least independent
   evidence in the change. Do not re-verify checkbox **state** (that is `apply`'s job), but
   **do verify the claim** wherever a task names something concrete:

   - Task names a file, migration, class, or test → **that artifact must exist and do what
     the task says.** A ticked task whose artifact is absent, empty, or does something else
     is a **gap**, and a specific one: quote the task and say what you found.
   - Task from the `## Coverage` matrix marked `COVERED` → the named test must exist **and**
     must have run green in the build gate. A test that exists but is skipped, disabled, or
     vacuous (asserts nothing) counts as a gap, not as coverage.
   - `MANUAL` and `WAIVED` rows → confirm the disposition is still recorded with its reason.
     Do not treat them as gaps; do flag any that lost their reason.
   - If the implementation looks complete but the boxes are largely **unchecked** (or vice
     versa), note it as an observation. Not a gap, but it reliably signals an apply stage
     that ended early.

6. **Cross-check each checkpoint against the evidence**

   For each checkpoint:
   - Search the evidence set collected in step 3 for implementation
   - Cite **file:line** for every verified checkpoint — a claim without a citation is a guess
   - Mark as **verified** if the code clearly satisfies it
   - Mark as **gap** if no evidence found or implementation contradicts it
   - Mark as **partial** if partially addressed but incomplete
   - Mark as **not applicable** if the checkpoint turned out irrelevant to this change

   Be pragmatic — look for intent and substance, not exact wording matches.

   **Attribution.** The manifest tells you which files this change *claims*. It does not by
   itself prove this change authored what is in them — a file a task names may have existed
   before. Where that distinction is load-bearing (a requirement the CR claims to *add*, sitting
   in code that predates it), say so rather than silently marking it verified. The cheap
   discriminator is the working-tree state from 3b: a path that is modified or untracked right
   now is this run's work.

7. **Produce the validation report**

   Display the full report (see output format below).

   **After the report:**
   - If called standalone: suggest next steps based on findings
   - If called from archive: return findings summary for archive to use (gaps count + list)

**Output Format**

```
## Validation Report: <change-name>

**Schema:** <schema-name>
**Scope:** manifest · <N> paths named by tasks, <N> read (<N> truncated) · <N> changed paths no task mentions
**Conformance:** <N> ticked tasks checked · <N> artifacts missing or divergent
**Coverage:** <N> scenarios — <N> COVERED (<N> green), <N> GROUPED, <N> MANUAL, <N> WAIVED
**Structural:** `openspec validate --strict` <passed | failed: ...>
**Checked:** <N> requirements/decisions
**Status:** <N> verified, <N> gaps, <N> partial

---

### Gaps  ← show only if gaps exist
- [ ] **[proposal]** Requirement X: no evidence found in code
- [ ] **[design]** Decision Y: implementation uses Z instead of W
- [ ] **[spec]** Rule A: handler missing for edge case B

### Partial  ← show only if partial items exist
- [~] **[design]** Decision X: implemented for happy path but error case missing

### Verified
- [x] **[proposal]** Goal: <description>
- [x] **[design]** Decision: <description>
- [x] **[spec]** Rule: <description>
...

---

**Conclusion:** <one of the following>
- ✓ Implementation matches spec — ready to archive
- ⚠ Minor gaps found — review before archiving
- ✗ Significant gaps found — recommend fixing before archiving
```

**Output When No Spec Artifacts Found**

```
## Validation Report: <change-name>

No spec artifacts found to validate against.

The change may have been created without proposal/design artifacts,
or the schema does not produce them.

Skipping validation.
```

**Guardrails**
- Be pragmatic: look for intent, not literal matches
- Don't fail on missing tasks.md — tasks are tracked separately by apply
- Don't validate out-of-scope items — only what the spec claims this change does
- **Never scope by diffing.** No `git diff <base>`, no `main...HEAD`, no commit ranges — the
  manifest in step 3 is the scope. Diffs are how a sibling CR's code came to satisfy this
  CR's checkpoints. `git status` is used only to spot unplanned work, never as the evidence set
- Never `git add` (or `git add -N`) — banned by the git guardrails and unnecessary here
- A ticked task naming an artifact that does not exist is a gap, not an observation
- If the evidence set is empty or very small, note it — may indicate no implementation yet
- Always state how you scoped the evidence, so a mis-scope is diagnosable from the report
- Gaps are informational, not blockers — the user decides whether to fix or proceed.
  **When invoked from `openspec-flow`, the flow's Issue policy governs what happens next**
  (fold minimal fixes, halt on anything larger); report gaps plainly and let the spine
  adjudicate rather than softening them into notes
- Keep gap descriptions specific: what was specified, what was found (or not found)
- Scope exclusions in proposal are also checkpoints — verify they weren't accidentally implemented
